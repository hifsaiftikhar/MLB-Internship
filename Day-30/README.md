## 📋 Overview
This project upgrades the Day-29 AI Video Processing API to enterprise-grade production standards by implementing:
1. **User Authentication**: Secure user registration and login with bcrypt password hashing.
2. **Stateless JWT Tokens**: Signed JSON Web Tokens (HMAC-SHA256) for secure, stateless session management.
3. **Role-Based Access Control (RBAC)**: Distinct permissions for `user` and `admin` roles.
4. **Protected AI Endpoints**: Restricting video processing, job viewing, downloading, and deletion to authenticated and authorized users.
5. **Automated Security Test Suite**: 16 comprehensive unit & integration tests covering all critical authentication and authorization edge cases.

## 🏗️ System Architecture

```
Client (User / Admin / Docs)
         │
         ├── 1. POST /auth/register ──> Salted bcrypt hash ──> SQLite (users table)
         ├── 2. POST /auth/login    ──> Verify password   ──> Return Signed JWT Token
         │
         ▼ (Send Header: "Authorization: Bearer <token>")
FastAPI Request Pipeline
         │
         ├── [get_current_user Dependency] ──> Decode & Verify JWT Signature/Expiration
         │
         ▼
Protected Endpoints (/video/process, /jobs/, /jobs/{id}, /video/result/{id})
         │
         ├── Role Check:
         │     ├── User: Filter query to `user_id == current_user.id` (403 Forbidden on foreign jobs)
         │     └── Admin: Query all jobs across all users
         ▼
AI Worker & Database Engine (YOLO Detector + SQLite)
```

## 🔑 Key Concepts & Technical Explanations

### 1. How Registration Works
1. The client submits a registration request to `POST /auth/register` containing:
   * `username` (string, unique)
   * `email` (valid email format, unique)
   * `password` (plain text string)
   * `role` (optional: `"user"` or `"admin"`, defaults to `"user"`)
2. The endpoint verifies that neither the username nor the email already exists in the database. If either is taken, it returns `HTTP 400 Bad Request` with an informative error message.
3. The password is immediately hashed using salted `bcrypt`. Plain-text passwords are never stored in memory longer than necessary and are **never** written to the database or logs.
4. The user record is saved to SQLite, and `HTTP 201 Created` is returned.

### 2. How Passwords Are Protected
* **Salting**: Every password is hashed with a cryptographically secure random salt generated by `bcrypt.gensalt()`. Even if two users choose the exact same password, their stored hashes will look completely different, preventing rainbow table attacks.
* **Work Factor (Cost)**: `bcrypt` is intentionally computationally intensive (adaptive cost factor 12), making brute-force dictionary attacks practically infeasible.
* **Length Truncation**: Standard bcrypt accepts up to 72 bytes. Our service encodes the string to UTF-8 and safely caps it at 72 bytes to avoid buffer errors.
* **Constant-Time Verification**: `bcrypt.checkpw()` performs comparisons in constant time, preventing timing-analysis side-channel attacks.

### 3. How JWT Authentication Works
1. Upon submitting valid credentials to `POST /auth/login`, the server generates a JSON Web Token (JWT).
2. **Payload Structure**:
   * `sub`: Subject identifier (the user's username).
   * `role`: User role (`"user"` or `"admin"`).
   * `exp`: Expiration timestamp in UTC (configured via `ACCESS_TOKEN_EXPIRE_MINUTES`).
3. **Signature**: The header and payload are encoded in Base64Url and signed using `HS256` (HMAC with SHA-256) using a secret key (`SECRET_KEY`) stored strictly in environment variables.
4. **Token Verification**: When protected routes are called, the client provides the token in the HTTP header:
   ```http
   Authorization: Bearer <access_token>
   ```
   FastAPI's `get_current_user` dependency intercepts the request, verifies the signature against `SECRET_KEY`, checks that `exp` has not expired, and fetches the user object from the database.

### 4. Authentication vs. Authorization

| Concept | Question Answered | Implementation in This Project |
| :--- | :--- | :--- |
| **Authentication (AuthN)** | *"Who are you?"* | Verified at `POST /auth/login` and validated via `get_current_user` using JWT. |
| **Authorization (AuthZ)** | *"What are you allowed to do?"* | Enforced via `current_user.role` checks and database ownership filters (`job.user_id == current_user.id`). |

### 5. Access Matrix: User vs. Admin

| Endpoint | Method | Unauthenticated | Normal User (`role: user`) | Admin (`role: admin`) |
| :--- | :---: | :---: | :---: | :---: |
| `/` | `GET` | ✅ Allowed | ✅ Allowed | ✅ Allowed |
| `/health` | `GET` | ✅ Allowed | ✅ Allowed | ✅ Allowed |
| `/auth/register` | `POST` | ✅ Allowed | ✅ Allowed | ✅ Allowed |
| `/auth/login` | `POST` | ✅ Allowed | ✅ Allowed | ✅ Allowed |
| `/auth/me` | `GET` | ❌ `401 Unauthorized` | ✅ Views own profile | ✅ Views own profile |
| `/video/process` | `POST` | ❌ `401 Unauthorized` | ✅ Uploads & starts job | ✅ Uploads & starts job |
| `/jobs/` | `GET` | ❌ `401 Unauthorized` | ✅ Views **only own jobs** | ✅ Views **all users' jobs** |
| `/jobs/{id}` | `GET` | ❌ `401 Unauthorized` | ✅ Only if job owner (else `403`) | ✅ Views any job |
| `/jobs/{id}` | `DELETE` | ❌ `401 Unauthorized` | ✅ Only if job owner (else `403`) | ✅ Can delete any job |
| `/video/result/{id}` | `GET` | ❌ `401 Unauthorized` | ✅ Only if job owner (else `403`) | ✅ Can download any result |

## ⚙️ Environment Variables (`.env.example`)

To protect sensitive keys, secrets are loaded via environment variables and `.env` is excluded in `.gitignore`. A template file [`.env.example`](file:///c:/Users/HP/Desktop/MLB-Internship/Day-30/.env.example) is provided:

```env
# Secret key used for signing JWT access tokens (use a long, random string in production)
SECRET_KEY=your_secure_random_jwt_secret_key_change_in_production

# JWT signing algorithm (standard HMAC SHA-256)
ALGORITHM=HS256

# JWT token expiration time in minutes
ACCESS_TOKEN_EXPIRE_MINUTES=30

# Database connection URL (defaults to SQLite local file)
DATABASE_URL=sqlite:///./app.db
```

## ▶️ How to Run the Application & Tests

### 1. Install Dependencies
```bash
pip install -r requirements.txt
```

### 2. Start the Server
```bash
uvicorn app.main:app --reload --port 8000
```
Visit **`http://127.0.0.1:8000/docs`** for interactive Swagger API documentation. Use the green **"Authorize"** button to log in and test protected routes directly.

### 3. Run the Automated Tests
```bash
pytest tests/test_api.py -v
```
*(Or directly: `python tests/test_api.py`)*
